# แผนดำเนินการจริง (Execution Plan)

เอกสารนี้ต่างจากแผน 01-07 ตรงที่ **เป็นแผนโครงการ**: ลำดับงานตามสัปดาห์ จุดตัดสินใจ go/no-go เส้นทางวิกฤต งานรายวันของช่วงแรก และกฎตัดขอบเขตเมื่องานช้า แผน 01-07 คือ "ทำอะไรในแต่ละระยะ" ส่วนไฟล์นี้คือ "ทำเมื่อไร ตามลำดับไหน และหยุดหรือไปต่อเมื่อไร"

## 1. สรุป

- **ระยะเวลารวม:** ประมาณ **12-13 สัปดาห์** (ราว 63 วันทำงาน) สำหรับระบบครบวงจรโดยคนเดียวเต็มเวลา ใช้ UI v1 (ขยายหน้า HTML ต้นแบบ) และเพิ่มอีก 3-4 สัปดาห์ถ้าทำ UI v2 (แอป React เต็มรูปแบบตามแผน 07) ตัวเลขคำนวณจากผลรวมตารางงานย่อยของแผน 01-06 (52.5 วัน ตัดงาน Runner โหมด B กับหน้าติดตามสดออกรอบแรก) บวกงานเตรียมและงานเสริมในแผนนี้ (ตัดสินใจ, ข้อมูลนำร่อง, รอบเทรนที่สอง, เก็บงาน)
- **กลยุทธ์:** ไม่สร้างระบบเต็มก่อนแล้วค่อยเทรน แต่สร้าง **โครงกระดูกที่ทำงานได้ครบวงจรก่อน** (ข้อมูลเล็ก → วัด baseline → เทรนนำร่อง → วัดซ้ำ → deploy) เพื่อรู้เร็วที่สุดว่า fine-tune ช่วยจริงหรือไม่ แล้วจึงขยาย
- **จุดตัดสินใจสำคัญ:** หลังวัด baseline (G1) และหลังรอบนำร่อง (G2) ถ้าผลไม่คุ้ม จะปรับหรือหยุดก่อนลงแรงส่วนที่เหลือ
- **เวลาที่ได้คำตอบแรก:** คำตอบว่า "fine-tune ช่วยจริงไหม" ได้ที่ประมาณสัปดาห์ที่ 7 (G2)

## 3. กลยุทธ์: โครงกระดูกก่อน แล้วขยาย

| ช่วง | สัปดาห์ | เป้าหมาย | ผลลัพธ์ที่ตอบได้ |
|---|---|---|---|
| A. พิสูจน์ | W0-W7 | ข้อมูลเล็ก + harness วัดผล + รอบนำร่อง + GGUF รอบแรก | "fine-tune ช่วยจริงไหม และไปต่อได้ไหม" |
| B. ขยาย | W8-W10 | ไปป์ไลน์สร้างข้อมูล ชุดข้อมูลใหญ่ รอบเทรนที่สอง | "ทำให้ได้ตามเป้า 1,500-3,000 ตัวอย่างและผ่าน gate เต็ม" |

รอบนำร่องใช้ข้อมูลราว 300-500 ตัวอย่าง (gold set ราว 100-120 ตัวอย่าง ขยายด้วยงาน P1) ไม่ใช่เป้าเต็ม 1,500-3,000 ซึ่งใช้กับรอบที่สอง เหตุผล: ถ้าท่อทั้งเส้นมีปัญหา (template, loss mask, การประเมิน) จะรู้ตั้งแต่ข้อมูลยังน้อย ระบบเตือนของแผน 03 ที่ว่าข้อมูลน้อยกว่า 1,000 จะขึ้นในรอบนำร่อง ซึ่งเป็นเรื่องปกติ

## 5. เส้นทางวิกฤต (Critical path)

```
D1-D11 (ตัดสินใจ) -> T1.0 -> T1.2 (validator) -> T2.2 (sandbox ดึงมาก่อน)
   -> T4.3-T4.6 (ชุดทดสอบ+ตัวตัดสิน) -> T4.10/T4.11 (baseline) -> G1
   -> P1 (ข้อมูลนำร่อง) -> T3.7 (เทรนนำร่อง) -> T5.4 (template parity) -> G2
   -> ระยะ 2 -> เทรนรอบสอง -> G3
```

งานที่ไม่อยู่บนเส้นวิกฤตและเลื่อนได้ถ้าจำเป็น: แดชบอร์ดขั้นสูง, Runner โหมด B, UI v2, ระยะ 6 ส่วนแดชบอร์ด

## 7. จุดตัดสินใจ Go / No-go

**G0 (สิ้น W0): พร้อมเริ่มไหม**
- [ ] base model โหลดบน llama-server ได้ และวัด tokens/s ที่ context 8k และ 32k แล้ว
- [ ] แท็ก `<tool_call>` ที่ฝังในเนื้อหาเรนเดอร์ตรงกับที่ chat template สร้างเอง (D2)
- [ ] ตรวจข้อกำหนดโมเดลครูแล้ว (D8)
- [ ] dry run เทรน 10 steps รอดที่ความยาว 8k บน GPU ที่เลือก (หรือมีแผนสำรอง)

ถ้าข้อใดไม่ผ่าน ให้แก้ก่อนเริ่ม W1 เพราะกระทบทั้งโครงการ

**G1 (กลางสัปดาห์ 5): baseline บอกอะไร ควร fine-tune ไหม**

| ผล baseline ของ base model | การตัดสินใจ |
|---|---|
| ด่าน 1-3 ผ่านเกณฑ์อยู่แล้วทุกด่าน | **ไม่ fine-tune** ใช้ base + circuit breaker + grammar ของ llama.cpp เก็บ workbench ไว้เป็นเครื่องมือ eval |
| ด่าน 1 (syntax) ต่ำแต่ด่านอื่นพอใช้ | ลอง grammar/JSON schema constraint ก่อน แล้ววัดใหม่ ถ้ายังไม่ถึงค่อยเทรน |
| ด่าน 2 (anti-loop) ต่ำ | เป็นเป้าหมายหลักของการเทรน และเพิ่ม circuit breaker ฝั่ง harness คู่กัน |
| ด่าน 3 (security) ต่ำหรือ false positive สูง | เป็นเป้าหมายของการเทรน แต่ให้ Semgrep/Bandit เป็นชั้นที่สองเสมอ ไม่พึ่งโมเดล 7B ตัวเดียว |
| โมเดลตั้งต้นตัวอื่นดีกว่าอย่างมีนัยสำคัญ | เปลี่ยน D1 ก่อนเทรน |

**G2 (สิ้น W7): รอบนำร่องคุ้มไหม**
โมเดลนำร่องไม่จำเป็นต้องผ่าน gate เต็ม เป้าหมายคือพิสูจน์ว่าทิศทางถูกและท่อทั้งเส้นทำงาน ไปต่อสเกลข้อมูลเมื่อครบทั้งหมดนี้ (เกณฑ์ปรับได้ แต่ต้องล็อกก่อนดูผล)
- [ ] ด่านที่เป็นเป้าหมายดีขึ้นอย่างมีนัยสำคัญ (ช่วงความเชื่อมั่น 95% ไม่ทับกับ base หรือดีขึ้นอย่างน้อย 10 จุด)
- [ ] Regression ลดไม่เกิน 3 จุด และไม่มีด่านที่เคยผ่านแล้วตก
- [ ] ผ่าน template parity และโมเดลรันบนเครื่องได้ตามเป้าความเร็ว

ถ้าไม่ผ่าน: วินิจฉัยตามลำดับ (1) template/loss mask (2) คุณภาพและความหลากหลายของข้อมูล (3) hyperparameter ทดลองซ้ำได้ไม่เกิน 2 รอบ ถ้ายังไม่ดี ให้ทบทวนกลยุทธ์ (เปลี่ยน base, เปลี่ยนเป้าหมายของ fine-tune, หรือใช้วิธีไม่เทรน) อย่าเพิ่มข้อมูลอย่างเดียวโดยไม่รู้สาเหตุ

**G3 (สิ้น W10): ขึ้น production ได้ไหม**
ผ่านทุกด่านตามแผน 04 หัวข้อ 8 (รวมความเร็ว และ E2E) บน quantization ที่จะใช้จริง

**G4 (สิ้น W12): วงจรเรียนรู้ต่อเนื่องใช้ได้ไหม**
เคสผิดพลาดหนึ่งเคสวนกลับเป็นข้อมูลเทรนได้ครบวงจร และรอบเทรนซ้ำผ่าน regression

## 9. การติดตามและการปรับแผน

**ทบทวนทุกสัปดาห์ (30 นาที)**
- งานที่เสร็จเทียบตาราง และจำนวนวันที่ใช้จริงเทียบประมาณการ
- ความเสี่ยงที่เปลี่ยนไปและสัญญาณเตือนที่โผล่มา
- ตัดสินใจว่าจะตัดหรือเลื่อนอะไรถ้าช้า

**กฎปรับแผน:** ถ้าสิ้น W2 ใช้เวลาเกินประมาณการมากกว่า 30% ให้คูณประมาณการที่เหลือด้วยอัตราเดียวกัน แล้วเลือกตัดตามลำดับด้านล่างจนตารางกลับมาพอดี

**ลำดับตัดขอบเขต (ตัดจากบนลงล่าง)**
1. UI v2 (React) ทั้งชุด คงไว้ที่ UI v1
2. แดชบอร์ดขั้นสูง และ Runner เทรนแบบ B (คงโหมด A)
3. ระยะ 6 ให้เหลือแบบกึ่งมือ (บันทึกเคสและส่งเข้าตัวแก้ไข ไม่ทำตัวคัดเคสอัตโนมัติ)
4. ลดเป้าข้อมูลรอบสอง (เช่น เหลือ 1,000-1,500) และเน้นหมวดที่ baseline อ่อนที่สุด
5. **ห้ามตัด:** ชุดทดสอบ frozen, การตรวจ loss mask, template parity, gate ก่อน promote, rollback

**จัดลำดับความสำคัญ**

| ระดับ | รายการ |
|---|---|
| ต้องมี | ระยะ 1, 4, 3, 5 (วงจรหลัก), UI v1 ของระยะเหล่านี้ |
| ควรมี | ระยะ 2 (ไปป์ไลน์ข้อมูล), UI คิวรีวิว |
| ทำถ้ามีเวลา | ระยะ 6 เต็มรูปแบบ, แดชบอร์ดตัวชี้วัด, UI v2 |
| ยังไม่ทำ | หลายผู้ใช้, ระบบยืนยันตัวตน, ให้บริการผ่านเครือข่ายสาธารณะ |

## 10. ทรัพยากรและค่าใช้จ่าย

| รายการ | ตัวขับค่าใช้จ่าย | วิธีคุม |
|---|---|---|
| เวลา GPU เทรน | จำนวนตัวอย่าง × ความยาว × epochs | วัดเวลาต่อ step จาก dry run แล้วประมาณทั้งรอบก่อนกดเริ่ม เริ่มที่รอบนำร่องขนาดเล็ก |
| โมเดลครู (API) | จำนวน token ที่สร้างและจำนวนรอบเรียก | เพดานงบต่อสัปดาห์ แคชผลลัพธ์ ล็อตเล็กก่อน |
| พื้นที่จัดเก็บ | โมเดล 16-bit และ GGUF หลายเวอร์ชัน | เก็บ 3 เวอร์ชัน ลบ merged 16-bit หลังผ่าน gate |
| เวลาคนรีวิว | ข้อมูลที่ต้องตรวจ (sec 100%) | จำกัดจำนวนต่อวัน ใช้ปุ่มลัดในคิว |

ยังไม่ประมาณเป็นตัวเงิน เพราะราคาบริการและปริมาณใช้งานจริงยังไม่รู้ ให้ใส่ตัวเลขจริงหลังวัดจาก dry run และล็อตข้อมูลแรก

## 12. นิยามความสำเร็จของโครงการ

- โมเดลเวอร์ชัน production ผ่านทุกด่านตามเกณฑ์ในแผน 04 บน quantization ที่ใช้จริง
- วัดได้ว่าดีกว่า base อย่างน้อยในด่านที่เป็นเป้าหมาย โดยไม่มี regression เกินเกณฑ์
- ทำวงจรข้อมูล → เทรน → ประเมิน → deploy → rollback ซ้ำได้จาก UI โดยไม่แก้สคริปต์ด้วยมือ
- เคสผิดพลาดจากการใช้งานจริงวนกลับเป็นข้อมูลรอบถัดไปได้
