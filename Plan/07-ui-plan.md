# แผน UI ทั้งระบบ

**ประมาณการ:** UI v2 (แอป React เต็มรูปแบบ งาน U0-U9) รวม 25 วันทำงาน ซ้อนกับงาน UI ที่อยู่ในแผนแต่ละระยะราว 8-9 วัน จึงเพิ่มสุทธิราว 16-17 วัน

## 0. UI v1 และ UI v2

- **UI v1:** ขยายหน้า HTML ต้นแบบทีละชิ้นตามงาน UI ที่อยู่ในแผนแต่ละระยะ (T1.5, T1.9, T2.9, T3.5, T4.9, T5.6, T6.5, T6.7) พอสำหรับใช้งานจนถึง G4 และเป็นค่าตั้งต้นของแผนดำเนินการ (08)
- **UI v2:** แอป React ตามแผนนี้ทั้งชุด (หัวข้อ 3-14) ทำหลัง G4 หรือเมื่อ v1 ไม่พอ เพราะเป็นงานเสริมที่ใหญ่ที่สุดของโครงการ
- หัวข้อ 3-14 ด้านล่างเป็นสเปกของ UI v2 ส่วน v1 ทำเฉพาะหน้าที่จำเป็นต่อแต่ละระยะ

**หลักการ:** ทำ UI v1 ทีละชิ้นพร้อมแต่ละระยะ ไม่เก็บไว้ทำตอนท้าย

## 1. เป้าหมายและหลักการออกแบบ

UI คือหน้าควบคุมของวงจร **ข้อมูล → เทรน → ประเมิน → deploy → เก็บเคส** ต้องทำให้ทำงานถูกต้องได้ง่ายกว่าทำผิด

1. **ตามลำดับงาน (workflow-first):** เมนูเรียงตามขั้นตอน แต่ละหน้าบอกว่าขั้นถัดไปคืออะไร
2. **ตรวจทันทีและอธิบายได้:** ทุกข้อผิดพลาดบอกว่าผิดข้อไหน ทำไม และแก้อย่างไร
3. **ไม่ทำงานหายและไม่เสียบริบท:** บันทึกฉบับร่างอัตโนมัติ ทุกผลลัพธ์แสดงเวอร์ชันและ hash ที่ผูกอยู่
4. **ด่านความปลอดภัยเห็นชัด:** การ promote โมเดลและการลบข้อมูลต้องมีขั้นตอนยืนยันที่สมเหตุสมผล ส่วน rollback ต้องทำได้เร็วที่สุด
5. **ใช้บนมือถือได้ แก้งานหนักบนจอใหญ่:** ดูสถานะ อนุมัติ และ rollback ได้จากมือถือ ส่วนแก้ตัวอย่างยาวๆ สบายที่สุดบนเดสก์ท็อป
6. **แหล่งความจริงชุดเดียว:** ตัวตรวจข้อมูลอยู่ฝั่ง backend ที่เดียว UI เรียกใช้ ไม่เขียนซ้ำ

## 2. สถานะของต้นแบบปัจจุบัน

ไฟล์ `finetune-workbench.html` ที่สร้างไว้แล้ว

| มีแล้ว | ข้อจำกัดที่ต้องแก้เมื่อทำจริง |
|---|---|
| ตัวแก้ไขตัวอย่าง + ตัวตรวจทันที | ตัวตรวจเป็น JavaScript แยกจาก Python ต้องย้ายมาเรียก backend |
| แดชบอร์ดสัดส่วนหมวด | ข้อมูลอยู่ใน localStorage ของเบราว์เซอร์เดียว |
| สร้างสคริปต์เทรนและคำสั่ง GGUF | นับ token แบบประมาณจากตัวอักษร |
| กรอกผล eval และตัวตรวจ output | ไม่มีการรัน eval หรือเทรนจริง |
| บันทึกเคสที่พลาด | บันทึกไฟล์ได้เป็น .txt เท่านั้น |

ต้นแบบใช้เป็นแบบจำลองด้านหน้าตาและการไหลของงาน ส่วนตรรกะต้องย้ายไป backend

## 3. โครงสร้างเมนู (Information Architecture)

```
ภาพรวม (Dashboard)
ข้อมูล
  |- ตัวอย่าง (รายการ + ตัวแก้ไข)
  |- ชุดข้อมูล (เวอร์ชัน, แบ่ง train/val, ส่งออก)
  |- คิวรีวิว (ข้อมูลที่สร้างอัตโนมัติ)      [ระยะ 2]
  |- งานสร้างข้อมูล                          [ระยะ 2]
เทรน
  |- รันทั้งหมด
  |- สร้างรันใหม่ (config + pre-flight)
  |- ติดตามรัน
ประเมิน
  |- ชุดทดสอบ
  |- รันประเมิน + รายงาน
  |- เปรียบเทียบเวอร์ชัน
โมเดล
  |- ทะเบียนเวอร์ชัน (promote / rollback)
เคส (Active Learning)                        [ระยะ 6]
  |- คิวคัดเคส
  |- ตัวชี้วัดคุณภาพ
ตั้งค่า
```

**มือถือ:** แถบล่าง 5 ช่อง คือ ภาพรวม, ข้อมูล, เทรน, ประเมิน, เพิ่มเติม (โมเดล, เคส, ตั้งค่า) **เดสก์ท็อป:** แถบข้างซ้ายแสดงครบพร้อมป้ายจำนวนงานค้าง (คิวรีวิว, เคสใหม่)

## 7. ขั้นตอนใช้งานหลัก (User flows)

1. **สร้างตัวอย่าง:** S1 → S2 เลือกหมวด → แก้ → เห็นผลตรวจสด → บันทึก (ถ้ามี err ยังบันทึกเป็น draft ได้แต่เข้าชุดข้อมูลไม่ได้)
2. **ผลิตชุดข้อมูล → เทรน → ประเมิน → promote:** S3 สร้างเวอร์ชัน → S6 สร้างรัน ผ่าน pre-flight → S7 ติดตาม → S8 ดูรายงาน → S10 promote เมื่อ gate ผ่าน
3. **รีวิวข้อมูลอัตโนมัติ:** S5 สั่งสร้าง → S4 ไล่รีวิว (อนุมัติ/แก้/ทิ้ง) → ข้อมูลที่อนุมัติเข้า S1 พร้อมสถานะ approved
4. **Rollback:** S0 หรือ S10 → ปุ่มย้อนกลับ → สรุปว่าจะย้อนจากเวอร์ชันไหนไปไหน → ยืนยัน → สถานะอัปเดตทันที
5. **เคสสู่ข้อมูล:** S11 เปิดเคส → สร้างตัวอย่าง (เปิด S2 พร้อมข้อมูลเติมให้) → บันทึก → เข้าชุดข้อมูลรอบถัดไป

## 8. พฤติกรรมของ UI ที่ต้องกำหนดชัด

- **สถานะว่าง:** ทุกรายการมีข้อความอธิบายและปุ่มเริ่มต้น
- **สถานะโหลด/ผิดพลาด:** โครงกระดูก (skeleton) ขณะโหลด ข้อความผิดพลาดบอกสาเหตุและทางเลือก (ลองใหม่ หรือดู log)
- **งานยาว:** ทุกงาน (เทรน, eval, สร้างข้อมูล) มีสถานะและความคืบหน้า ปิดหน้าแล้วกลับมาเห็นสถานะเดิม
- **การเชื่อมต่อหลุด:** แถบแจ้ง และเชื่อมต่อ SSE ใหม่อัตโนมัติ
- **ป้องกันการแก้พร้อมกัน:** ตัวอย่างที่กำลังแก้แจ้งเตือนถ้ามีการเปลี่ยนจากที่อื่น
- **ไม่ให้ทำผิดจังหวะ:** ปุ่มเริ่มเทรนล็อกจน pre-flight ผ่าน ปุ่ม promote ล็อกจน gate ผ่าน พร้อมบอกเหตุผลที่ล็อก
- **ความโปร่งใสของเวอร์ชัน:** ทุกรายงานและรันแสดงเวอร์ชันข้อมูล, config และ hash ที่เกี่ยวข้อง

## 9. การตอบสนองตามขนาดจอและการเข้าถึง

- จุดสัมผัสอย่างน้อย 42 px, ข้อความหลักไม่เล็กกว่า 15 px
- จอแคบ: หนึ่งคอลัมน์ ตารางเลื่อนแนวนอนในกรอบของตัวเอง กราฟปรับความสูง
- จอกว้าง: แถบข้างซ้าย และแสดงตัวแก้ไขกับแผงผลตรวจเคียงกัน
- เดสก์ท็อป: ปุ่มลัดในคิวรีวิว (อนุมัติ, แก้, ทิ้ง, ถัดไป) และแสดงคำใบ้ปุ่มลัด
- สีคอนทราสต์ผ่านเกณฑ์ทั้งโหมดสว่างและมืด สถานะมีข้อความและไอคอนประกอบเสมอ
- รองรับการนำทางด้วยคีย์บอร์ดและ screen reader (label, aria-live สำหรับผลตรวจและสถานะรัน)
- เคารพการตั้งค่าลดการเคลื่อนไหว (prefers-reduced-motion)

## 10. สถาปัตยกรรม Frontend

| เรื่อง | ข้อเสนอ | เหตุผล |
|---|---|---|
| เฟรมเวิร์ก | Vite + React + TypeScript | มีหลายหน้าและสถานะซับซ้อนกว่าหน้า HTML เดียว |
| ข้อมูลจาก API | TanStack Query | แคช การรีเฟรช และสถานะโหลด |
| API client | สร้างอัตโนมัติจาก OpenAPI ของ FastAPI | ชนิดข้อมูลตรงกับ backend |
| เรียลไทม์ | SSE hook เชื่อมต่อใหม่อัตโนมัติ | ใช้กับ log และ metrics ของรัน |
| กราฟ | uPlot หรือไลบรารีกราฟเบา | ข้อมูล metrics จำนวนมาก |
| ตัวแก้ JSON/diff | CodeMirror | ไฮไลต์และตรวจโครงสร้างได้ |
| การตรวจข้อมูล | เรียก `/validate` แบบหน่วงเวลา (debounce ราว 300 ms) | ตัวตรวจอยู่ฝั่ง backend ที่เดียว |
| ฉบับร่าง | autosave ไปที่ backend เป็นสถานะ draft | ไม่หายเมื่อปิดหน้า |
| สไตล์ | CSS variables + CSS modules | ใช้ tokens ร่วมกับต้นแบบ |

ทางเลือก: ถ้าต้องการเบาที่สุด ให้คงหน้า HTML ต้นแบบต่อไปได้ในช่วงระยะ 1 แล้วย้ายเมื่อเริ่มระยะ 3 ที่ต้องมีหลายหน้าและข้อมูลสด

## 12. การทดสอบ UI

- **Component test (Vitest):** ValidationPanel, StatusChip, ConfirmAction, GateCard

## 14. ความเสี่ยงและวิธีรับมือ

| ความเสี่ยง | วิธีรับมือ |
|---|---|
| ตัวตรวจฝั่ง UI กับ backend ไม่ตรงกัน | ให้ backend เป็นแหล่งเดียว UI แค่แสดงผล |
| UI ทำท้ายสุดแล้วรั้งงานอื่น | ทำ UI v1 ทีละชิ้นพร้อมแต่ละระยะ ส่วน UI v2 ทำหลัง G4 |
| หน้ารายการตัวอย่างช้าเมื่อมีหลายพันรายการ | แบ่งหน้าและกรองฝั่งเซิร์ฟเวอร์ ใช้ virtual list ถ้าจำเป็น |
| กดผิดแล้ว promote หรือลบ | ConfirmAction พร้อมสรุปผลกระทบ และบล็อกด้วย gate |
| การสตรีม log หลุดบ่อย | เชื่อมต่อใหม่อัตโนมัติ และดึงย้อนหลังจากไฟล์ metrics |
| จอเล็กแก้ตัวอย่างยาวไม่สะดวก | จัดเป็นโหมดเต็มจอต่อข้อความ และแนะนำเดสก์ท็อปสำหรับงานแก้หนัก |

## 15. ประเด็นที่ต้องตัดสินใจก่อนเริ่ม

1. ใช้คนเดียวหรือหลายคน (ถ้าหลายคนต้องมีการยืนยันตัวตนและบันทึกว่าใครอนุมัติอะไร)
2. รันบนเครื่องตัวเองอย่างเดียว หรือเปิดให้เข้าผ่านเครือข่าย (มีผลต่อความปลอดภัยของ endpoint ที่สั่งเทรนและ promote)
3. ใช้ Vite + React ตั้งแต่ต้น หรือคงหน้า HTML ต้นแบบ (UI v1) ไปก่อน (ค่าตั้งต้นในแผน 08 คือ v1 ถึง G4 แล้วค่อยทำ v2)
