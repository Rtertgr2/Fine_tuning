# ระยะที่ 1: Dataset Studio

**ประมาณการ:** ประมาณ 9-10 วันทำงาน **ต้องทำก่อน:** ไม่มี **เริ่มระยะอื่นได้เมื่อจบ:** ระยะ 4 และ 2

## 1. เป้าหมาย

สร้าง สอบ และส่งออกชุดข้อมูล fine-tune ได้จากที่เดียว โดยระบบตรวจความถูกต้องให้อัตโนมัติ และควบคุมสัดส่วนหมวดกับคุณภาพของข้อมูลได้

## 2. ขอบเขต

**ทำ**
- ตัวแก้ไขตัวอย่างแบบ multi-turn พร้อมตัวตรวจทันที
- ฐานข้อมูลตัวอย่างพร้อมสถานะ (draft, approved, rejected)
- นำเข้าและส่งออก .jsonl
- แบ่ง train/val แบบกันข้อมูลรั่ว และสร้างเวอร์ชันชุดข้อมูลพร้อม manifest
- แดชบอร์ดสัดส่วนและคุณภาพ

**ไม่ทำ (ทำในระยะอื่น)**
- การสร้างข้อมูลอัตโนมัติด้วยโมเดลครู (ระยะ 2)
- การเก็บเคสจาก log จริง (ระยะ 6)

## 3. ข้อกำหนดเบื้องต้น

- ตัดสินใจ base model (เพื่อใช้ tokenizer และ chat template ตัวจริง)
- ตัดสินใจนิยามค่า status ของหมวดวิเคราะห์แผน (แผนเดิมกำหนดฟิลด์ แต่ยังไม่ระบุค่า) เช่น `APPROVED` หรือ `NEEDS_REVISION`
- ตัดสินใจโครงสร้างของ security review output (แนะนำ: status + issues[] โดยแต่ละ issue มี file, line, type, severity, fix)

## 5. กฎการตรวจ (Validators)

ทุกกฎมีระดับ **err** (ห้ามเข้าชุดข้อมูล) หรือ **warn** (เตือน)

**ทั่วไป**

| รหัส | กฎ | ระดับ |
|---|---|---|
| C1 | role ถูกต้องและเรียงถูก (system, user, assistant, tool) | err |
| C2 | ทุกข้อความมีเนื้อหา | err |
| C3 | มี assistant อย่างน้อยหนึ่งข้อความ | err |
| C4 | จำนวน token หลัง render template ไม่เกิน max length | err |
| C5 | ไม่พบความลับ (คีย์, รหัสผ่าน, private key) | err |
| C6 | ไม่ซ้ำกับตัวอย่างอื่น (hash ตรง) และไม่ใกล้เคียงเกินเกณฑ์ (near-duplicate) | err / warn |

**หมวด tool**

| รหัส | กฎ | ระดับ |
|---|---|---|
| T1 | ทุก `<tool_call>` แปลงเป็น JSON ได้ และแท็กเปิดปิดครบ | err |
| T2 | ชื่อ tool อยู่ใน registry (git_checkout, read_file, write_file) | err |
| T3 | มี argument ครบและชนิดถูก | err |
| T4 | ทุก tool_call ตามด้วยผลลัพธ์ role tool | err |
| T5 | จำนวน tool_call 3-6 ครั้ง | warn |
| T6 | เนื้อหา write_file ต้องเป็นไฟล์เต็ม ไม่มีเครื่องหมาย diff หรือข้อความประเภท "ส่วนที่เหลือเหมือนเดิม" | err |

**หมวด loop**

| รหัส | กฎ | ระดับ |
|---|---|---|
| L1 | มีผลลัพธ์ tool ที่ล้มเหลวอย่างน้อยหนึ่งครั้ง | warn |
| L2 | หลังล้มเหลว tool_call ถัดไปต้องต่างจากเดิม (ชื่อหรือ argument) | err |
| L3 | ไม่มี tool_call ซ้ำเหมือนเดิมทุกตัวอักษรหลังล้มเหลว | err |
| L4 | มีตัวอย่างที่จบด้วย "หยุดแล้วรายงานว่าทำไม่ได้" อย่างน้อย 15% ของหมวด | warn (ระดับชุด) |

**หมวด plan**

| รหัส | กฎ | ระดับ |
|---|---|---|
| P1 | คำตอบสุดท้ายเป็น JSON แท้ ไม่มี code fence หรือคำทักทาย | err |
| P2 | มีฟิลด์ status, target_version, critique, final_plan | err |
| P3 | status อยู่ในค่าที่กำหนด | err |
| P4 | target_version เป็นรูปแบบเวอร์ชันที่ถูกต้อง | warn |

**หมวด sec**

| รหัส | กฎ | ระดับ |
|---|---|---|
| S1 | คำตอบสุดท้ายเป็น JSON แท้ | err |
| S2 | status เป็น PASS หรือ REJECT | err |
| S3 | REJECT ต้องมี issues และทุก issue มี file, line, type, severity, fix (ตามที่ล็อกใน D4) | err |
| S4 | บรรทัดที่ระบุต้องมีอยู่จริงใน diff ที่ให้ | err |
| S5 | PASS ต้องไม่มี issues | warn |
| S6 | สัดส่วน PASS ของหมวดอยู่ที่ราว 50% | warn (ระดับชุด) |
| S7 | ครอบคลุมประเภทช่องโหว่ตามรายการ (OWASP Top 10, SQL Injection, resource leak, insecure deserialization) อย่างน้อยประเภทละ N ตัวอย่าง | warn (ระดับชุด) |

## 8. แนวทางเขียนตัวอย่าง (Style guide สำหรับ gold set)

- เขียน system prompt ให้คงที่ต่อหมวด ไม่ใช้ข้อความที่ต่างกันเล็กน้อยแบบสุ่ม
- แต่ละตัวอย่างต้องมีเป้าหมายเดียวที่ชัด
- หมวด tool: ให้ครอบคลุมทั้งกรณีเขียนไฟล์ใหม่ แก้ไฟล์เดิม (อ่านก่อน แล้วเขียนไฟล์เต็ม) และเปลี่ยน branch
- หมวด loop: กระจายชนิดข้อผิดพลาด (ไฟล์ไม่พบ, syntax error, ถูกนโยบายบล็อก) และกระจายวิธีแก้ (ตรวจด้วย read_file, เปลี่ยน path, หยุดและรายงาน)
- หมวด sec: ทุก diff ที่ REJECT ต้องมีคู่ diff สะอาดที่ใกล้เคียงกัน เพื่อไม่ให้โมเดลเรียนแค่ลักษณะผิวเผิน
- ความยาวหลากหลาย รวมตัวอย่างยาวที่ใกล้ max length ด้วย

## 9. การทดสอบ

- Unit test ต่อกฎ: อย่างน้อย 1 กรณีผ่านและ 1 กรณีไม่ผ่าน
- Round-trip: นำเข้า → ส่งออก → นำเข้าอีกครั้ง ต้องเหมือนเดิมทุกไบต์ที่มีความหมาย
- ทดสอบการแบ่งข้อมูล: ไม่มี group เดียวกันข้ามฝั่ง train/val
- ทดสอบซ้ำ: seed เดิมได้การแบ่งเดิม
- เทียบจำนวน token กับ tokenizer ตัวจริง

## 10. เกณฑ์ตรวจรับ (Definition of Done)

- [ ] สร้างและส่งออกชุดข้อมูล 100 ตัวอย่างที่ผ่านการตรวจทุกกฎระดับ err ได้จากหน้าเดียว
- [ ] ตัวตรวจฝั่ง backend และหน้า UI ให้ผลตรงกัน
- [ ] การแบ่ง train/val ไม่มีการรั่วข้าม group และรันซ้ำได้ผลเดิม
- [ ] manifest บันทึก seed, จำนวนต่อหมวด และ hash ของไฟล์
- [ ] มี gold set ครบทุกหมวด

## 11. ความเสี่ยง

| ความเสี่ยง | วิธีรับมือ |
|---|---|
| รูปแบบ tool call ไม่ตรงกับ chat template | ทำ T1.0 ก่อน และทดสอบเรนเดอร์ด้วย template จริง |
| นับ token คลาดเคลื่อน | ใช้ tokenizer จริงหลัง render แทนการประมาณ |
| ตัวตรวจเข้มหรือหลวมเกินไป | ปรับกฎจาก gold set และเก็บสถิติว่ากฎไหนตัดข้อมูลมากผิดปกติ |
| ตัวอย่างเขียนมือน้อยและแคบ | ใช้ gold set เป็นตัวตั้งต้นให้ระยะ 2 ขยายความหลากหลาย |
