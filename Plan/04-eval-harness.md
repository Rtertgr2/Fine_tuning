# ระยะที่ 4: Eval Harness

**ประมาณการ:** 11-12 วันทำงาน **ต้องทำก่อน:** ระยะ 1 (สคีมาและ validator) และ sandbox จากระยะ 2 (T2.2 ถูกดึงมาทำก่อนในสัปดาห์ที่ 3 ตามแผน 08) **ส่งผลให้:** ระยะ 3 และ 5

## 1. เป้าหมาย

วัดโมเดลอย่างเป็นระบบและซ้ำได้ ด้วยชุดทดสอบที่ไม่ปนกับข้อมูลเทรน ให้ผลผ่าน/ไม่ผ่านต่อด่าน และเปรียบเทียบ base, เวอร์ชันก่อนหน้า และเวอร์ชันใหม่ได้ในรายงานเดียว

## 2. ขอบเขต

**ทำ**
- ชุดทดสอบแบบ frozen พร้อมเวอร์ชันและ hash
- 4 ด่านตามแผนเดิม บวก false positive, regression และ end-to-end
- รายงานพร้อมช่วงความเชื่อมั่น และ gate ก่อน deploy

**ไม่ทำ**
- การเทรน (ระยะ 3)

## 3. ข้อกำหนดเบื้องต้น

- llama-server รันโมเดลได้ (ทั้ง base และเวอร์ชันที่จะทดสอบ)
- Sandbox และ tool จริง (ใช้ตัวเดียวกับระยะ 2)
- ตัดสินใจเกณฑ์ผ่านของแต่ละด่านล่วงหน้าและบันทึกไว้ **ก่อน** ดูผล

## 4. ชุดทดสอบ (Test suites)

**หลักการ**
- แยกจาก train และ val ตั้งแต่ต้น ใช้ group คนละชุด
- Frozen: แก้ไม่ได้หลังสร้าง มีเวอร์ชันและ hash ถ้าต้องเพิ่ม ให้สร้างเวอร์ชันใหม่
- ตรวจ overlap กับชุดข้อมูลเทรนทุกครั้งที่สร้างชุดข้อมูลใหม่

| Suite | ขนาดขั้นต่ำ | เนื้อหา |
|---|---|---|
| tool_syntax | 100 prompts | งานหลากหลายที่ต้องเรียก tool ผ่าน sandbox จริง |
| anti_loop | 40 สถานการณ์ | ฉีดความผิดพลาดหลายชนิด (ไฟล์ไม่พบ, syntax error, ถูกบล็อก, branch ไม่มี) |
| security_vuln | 100 diffs | ช่องโหว่ครบประเภท อย่างน้อยประเภทละ 5 |
| security_clean | 100 diffs | diff สะอาด รวมตัวที่หน้าตาคล้ายโค้ดมีช่องโหว่ |
| plan_json | 50 แผน | ตรวจการตอบเป็น JSON แท้และฟิลด์ครบ |
| regression | HumanEval+ และ MBPP+ | ความสามารถโค้ดทั่วไป |
| e2e | 20-30 งานจริงของคุณ | งานที่ใช้ agent ทั้ง Plan → Code → Review |

ขนาดในแผนเดิมคือ 50 และ 20 ซึ่งน้อยเกินสำหรับสรุปผล (เช่น 17 จาก 20 ให้ช่วงความเชื่อมั่นกว้างมาก) จึงเพิ่มขนาดขั้นต่ำ

## 5. นิยามด่านและเกณฑ์ผ่าน

| ด่าน | วิธีวัด | เกณฑ์ผ่าน |
|---|---|---|
| 1 Tool syntax | ทุก tool_call ผ่าน `json.loads`, ชื่อ tool ถูก, argument ครบและชนิดถูก, แท็กครบ | 100% |
| 2 Anti-loop | หลังเกิด error ภายใน 2 รอบต้อง (ก) เรียกต่างจากเดิม (ชื่อหรือ argument) หรือ (ข) หยุดพร้อมรายงานเหตุผลที่ถูกต้อง ไม่ผ่านถ้าเรียกซ้ำเหมือนเดิม, JSON พัง หรือรายงานว่าสำเร็จทั้งที่ล้มเหลว | อย่างน้อย 90% |
| 3a Security catch | diff มีช่องโหว่ ต้อง REJECT, ระบุ type ถูก และ line อยู่ในช่วงที่ถูกต้อง | อย่างน้อย 85% |
| 3b False positive | diff สะอาดที่ถูก REJECT ผิด | ไม่เกิน 10% |
| 3c JSON validity | ผลรีวิวเป็น JSON แท้และตรงสคีมา | 100% โดยวัดแบบ **ไม่ใช้** grammar เพื่อดูความน่าเชื่อถือของโมเดลเอง แล้ววัดซ้ำแบบใช้ grammar ที่จะใช้งานจริง |
| 4 ความเร็ว | tokens/s ของการสร้างข้อความที่ระดับ context ที่กำหนด | อย่างน้อย 30 tok/s ที่ context เต็ม 8k และรายงานที่ 16k และ 32k (แผนเดิมกำหนดที่เปิด context 32k ให้ยืนยันว่าจะใช้เกณฑ์ไหนก่อนล็อก) |
| R Regression | HumanEval+/MBPP+ pass@1 เทียบ base | ลดไม่เกิน 3 จุด |
| E End-to-end | อัตราสำเร็จของงานจริง | ไม่ต่ำกว่า base และมากกว่าเวอร์ชันก่อนหน้าหรือเท่ากัน |

เกณฑ์เหล่านี้เป็นค่าตั้งต้นที่ปรับได้ ให้ล็อกค่าลง config ของชุดทดสอบก่อนรันครั้งแรก

## 6. การออกแบบ Harness

```
eval/
  suites/<name>/v001/cases.jsonl + manifest.json
  runners/            # tool_syntax.py, anti_loop.py, security.py, speed.py, regression.py, e2e.py
  clients/            # OpenAI-compatible client ต่อ llama-server
  reports/<run_id>/   # results.json, report.html
```

- เรียกโมเดลผ่าน llama-server (API แบบ OpenAI) โดยอุณหภูมิต่ำหรือ 0 เพื่อผลซ้ำได้ ถ้าต้องสุ่มให้รันหลายรอบและบันทึก seed
- ทดสอบทั้งโหมดที่ parse ข้อความดิบ (ตรงกับรูปแบบที่เทรน) และโหมด tools ของ API เพื่อจับปัญหา template
- ด่าน 1 และ 2 รันลูป agent จริงกับ sandbox ไม่ใช่แค่ตรวจข้อความ โดยจำกัดจำนวนรอบสูงสุด (เช่น 8) เพื่อจับลูป
- ด่าน security เปรียบเทียบกับ Semgrep/Bandit เป็นเส้นฐาน เพื่อรู้ว่าโมเดลเพิ่มอะไรจริง
- ด่านความเร็ว: ใช้ค่า timings ที่ llama-server ส่งกลับ (tokens/s ของ prompt และของการสร้าง) วัดที่ context ว่าง, 8k, 16k, 32k
- VRAM: อ่านจากบันทึกตอนโหลดของ llama-server และเครื่องมือมอนิเตอร์ของการ์ดที่ใช้ (เช่น nvtop, radeontop, intel_gpu_top)
- Regression: ใช้ evalplus หรือชุดเครื่องมือที่เทียบเท่า

## 7. สถิติและการรายงาน

- รายงานทุกอัตราพร้อมช่วงความเชื่อมั่น 95% (Wilson interval) และจำนวนตัวอย่าง
- ตัวอย่างน้อยกว่า 30 ต้องติดป้ายเตือนว่าสรุปไม่ได้
- เปรียบเทียบแบบจับคู่กับ base และเวอร์ชันก่อนหน้าบนกรณีทดสอบเดียวกัน แสดงกรณีที่แย่ลงเป็นรายการ
- แจกแจงความล้มเหลวตามชนิด (JSON พัง, ชื่อ tool ผิด, ลูป, ช่องโหว่ที่พลาดตามประเภท) เพื่อชี้ว่าต้องเพิ่มข้อมูลด้านไหน
- รายงานสรุปผลผ่าน/ไม่ผ่านต่อด่าน และผลรวม gate

## 8. Gate ก่อน deploy

- เวอร์ชันจะถูกทำเครื่องหมาย `candidate` ได้ก็ต่อเมื่อผ่านด่าน 1, 2, 3, R
- จะเป็น `production` ได้เมื่อผ่านครบทุกด่านรวมความเร็วและ E2E บน quantization ที่จะใช้จริง
- ผล eval ผูกกับ manifest ของโมเดล เพื่อย้อนดูได้ภายหลัง

## 10. การทดสอบตัวฮาร์เนสเอง

- ใช้ "โมเดลปลอม" ที่ตอบถูกทุกข้อและที่ตอบผิดทุกข้อ เพื่อยืนยันว่าตัวตัดสินให้ 100% และ 0% ตามลำดับ
- ทดสอบว่ารันซ้ำได้ผลเหมือนเดิมเมื่อคงอุณหภูมิและ seed
- ทดสอบตัวตรวจ overlap ระหว่าง suite กับชุดข้อมูลเทรนด้วยตัวอย่างที่ตั้งใจให้ซ้ำ
