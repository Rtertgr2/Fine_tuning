# ระยะที่ 6: Active Learning

**ประมาณการ:** ประมาณ 8 วันทำงาน **ต้องทำก่อน:** ระยะ 1, 4, 5 (มีโมเดลใช้งานจริงและ harness วัดผล) **ผลลัพธ์:** วงจรที่เคสผิดพลาดวนกลับเป็นข้อมูลเทรนรอบถัดไป

## 1. เป้าหมาย

เก็บพฤติกรรมของ agent จริง คัดเคสที่พลาดอย่างมีระบบ เขียนเฉลยที่ถูก และส่งกลับเข้าชุดข้อมูลรอบถัดไป โดยไม่ทำให้ข้อมูลรั่ว ไม่มีความลับหลุด และไม่ทำให้โมเดลเอียงไปทางเดียว

## 2. ขอบเขต

**ทำ**
- บันทึก log แบบมีโครงสร้างจาก agent และ redact ความลับตอนเขียน
- ตัวคัดเคสอัตโนมัติและคิวติดป้าย
- ตัวแก้ไขเฉลยที่เติมข้อมูลจากเคสให้อัตโนมัติ
- นโยบายผสมข้อมูลรอบใหม่ และรอบเทรนซ้ำที่มี regression eval ทุกครั้ง
- แดชบอร์ดติดตามคุณภาพตามเวอร์ชันโมเดล

**ไม่ทำ**
- การเทรนแบบ online หรือปรับโมเดลอัตโนมัติโดยไม่มีคนตรวจ

## 3. ข้อกำหนดเบื้องต้น

- Agent harness ส่งเหตุการณ์แบบมีโครงสร้างได้ (แก้โค้ด harness ถ้าจำเป็น)
- ตัดสินใจนโยบายความเป็นส่วนตัว: เก็บอะไร เก็บนานเท่าไร ใครเข้าถึงได้ และต้องเปิดใช้ต่อโปรเจกต์
- ทะเบียนเวอร์ชันโมเดลจากระยะ 5 เพื่อผูกทุกเหตุการณ์กับเวอร์ชันที่ตอบ

## 4. โครงสร้าง log

หนึ่งเซสชันเป็น JSONL ต่อบรรทัดต่อเหตุการณ์

```json
{"session_id":"s_123","ts":"2026-...","model_version":"v0.2.0","state":"plan|code|review",
 "event":"message|tool_call|tool_result|circuit_breaker|verdict|override|outcome",
 "data":{...},"project":"..."}
```

- ทุกเหตุการณ์มี `model_version` และ `state`
- **Redact ตอนเขียน** ไม่ใช่ตอนอ่านภายหลัง: ใช้ตัวสแกนความลับและรูปแบบข้อมูลส่วนบุคคล แล้วแทนด้วยตัวยึดตำแหน่ง
- กำหนดระยะเวลาเก็บ (retention) และลบอัตโนมัติเมื่อครบ

## 5. ตัวคัดเคสอัตโนมัติ

| สัญญาณ | ประเภทเคส | หมายเหตุ |
|---|---|---|
| Circuit breaker ทำงาน | loop | ตัวชี้วัดหลักของการติดลูป |
| tool_call ซ้ำเหมือนเดิมอย่างน้อย 2 ครั้ง | loop | ก่อนถึง circuit breaker |
| JSON หรือ tool_call พัง | syntax | ส่งเข้าหมวด tool หรือ plan ตามบริบท |
| หลัง tool error ไม่เปลี่ยนวิธี | loop | ตรวจตามกฎเดียวกับหมวด loop |
| Reviewer ตอบ PASS แต่เทสต์ล้มหรือถูกแก้ย้อนภายหลัง | false negative | ป้ายมาจากผลจริง |
| Reviewer ตอบ REJECT แต่คนกดยืนยันว่าปลอดภัย | false positive | ต้องมีการยืนยันจากคน |
| ผู้ใช้ยกเลิกหรือย้อนงานของ agent | อื่นๆ | ตรวจดูทีละเคส |

นอกจากเคสผิดพลาด ให้สุ่มเคสที่ **สำเร็จ** เข้าคิวด้วยในสัดส่วนหนึ่ง เพื่อไม่ให้ข้อมูลรอบใหม่มีแต่ความล้มเหลว

## 6. คิวติดป้ายและเขียนเฉลย

1. เปิดเซสชันเป็นไทม์ไลน์ ข้อความ tool call ผลลัพธ์ และจุดที่พลาดถูกไฮไลต์
2. ผู้ตรวจเลือกชนิดความผิดพลาด (ติดลูป, false positive, false negative, JSON พัง ฯลฯ)
3. เปิดตัวแก้ไขของระยะ 1 ที่เติมบทสนทนาเดิมไว้ให้ ผู้ตรวจแก้ให้เป็น **เส้นทางที่ถูกต้องทั้งเส้นทาง** รวมผลลัพธ์ tool ที่ล้มเหลวและการรับมือ ไม่ใช่แค่ประโยคสุดท้าย
4. ผ่าน validator ระยะ 1 และตัวสแกนความลับอีกรอบ
5. หมวด sec ต้องมีผู้ตรวจคนที่สองยืนยันก่อนอนุมัติ
6. บันทึกเหตุผลที่ตัดสิน เพื่อใช้สรุปว่าจุดอ่อนของโมเดลอยู่ตรงไหน

## 7. นโยบายผสมข้อมูลรอบใหม่

- ตัวอย่างจาก Active Learning ไม่ควรเกินราว 30% ของชุดข้อมูลรอบใหม่ (ปรับได้) ที่เหลือเป็นข้อมูลเดิมที่ยังผ่านการตรวจ เพื่อกันโมเดลลืมของเดิม (replay)
- ผสมเคสที่สำเร็จเพื่อคงพฤติกรรมที่ถูก
- ตรวจซ้ำและ near-duplicate กับชุดเดิมทุกครั้ง
- **กันชุดทดสอบรั่ว:** เคสจาก log ต้องแบ่งเป็นส่วนเข้าเทรนและส่วนที่กันไว้เป็นชุด regression ใหม่ (ไม่เอาเคสเดียวกันไปทั้งสองฝั่ง) โดยแบ่งตาม session หรือ project ที่ต่างกัน
- สร้างเป็นชุดข้อมูลเวอร์ชันใหม่ผ่านระยะ 1 แล้วเทรนต่อผ่านระยะ 3 และผ่านระยะ 4 และ 5 ตามปกติ

## 8. จังหวะการเทรนซ้ำ

- เทรนเมื่อมีเคสที่อนุมัติใหม่ถึงเกณฑ์ (ตั้งต้นราว 150 เคส หรือตามที่ปรับได้) หรือเมื่อตัวชี้วัดคุณภาพแย่ลงต่อเนื่อง ไม่ใช่ตามปฏิทินอย่างเดียว
- ทุกรอบต้องรัน regression eval เต็ม และเทียบกับเวอร์ชัน production ปัจจุบัน
- Deploy เฉพาะเมื่อผ่าน gate และดีกว่าหรือเท่าเดิมในตัวชี้วัดหลัก

## 9. แดชบอร์ดติดตาม

- อัตรา circuit breaker ต่อ 100 เซสชัน แยกตามเวอร์ชันโมเดล
- อัตรา tool error และอัตราที่โมเดลรับมือได้ภายใน 2 รอบ
- อัตรา false positive และ false negative ของ reviewer
- อัตราสำเร็จของงานและเวลาเฉลี่ยต่องาน
- จำนวนเคสในคิว อายุของเคส และสัดส่วนตามประเภท

## 11. การทดสอบ

- Redaction: ป้อน log ที่ฝังความลับหลายรูปแบบ ต้องไม่หลุดออกมาในฐานข้อมูลหรือชุดข้อมูล
- ตัวคัดเคส: ป้อนเซสชันจำลองที่มีลูป, JSON พัง และ reviewer ผิด ต้องเข้าคิวถูกประเภท
- ทดสอบการแบ่งชุด: ไม่มีเคสหรือ session เดียวกันในทั้ง train และ regression
- ซ้อมวงจรครบตั้งแต่ log ถึง deploy พร้อมวัดเวลา

- [ ] ไม่พบความลับในข้อมูลที่ผ่าน redaction ในการทดสอบ
- [ ] ทุกรอบเทรนซ้ำผ่าน regression eval ก่อน deploy
- [ ] แดชบอร์ดแสดงแนวโน้มตัวชี้วัดต่อเวอร์ชันโมเดล
- [ ] ซ้อมวงจรเต็มสำเร็จอย่างน้อยหนึ่งรอบ

## 13. ความเสี่ยง

| ความเสี่ยง | วิธีรับมือ |
|---|---|
| ความลับหรือข้อมูลส่วนบุคคลหลุดใน log | redact ตอนเขียน สแกนซ้ำก่อนเข้าชุดข้อมูล และมี retention |
| ข้อมูลเอียงไปทางเคสล้มเหลว | ผสมเคสสำเร็จและข้อมูลเดิม จำกัดสัดส่วน AL |
| เคสเดียวกันอยู่ทั้ง train และ regression | แบ่งตาม session/project และตรวจซ้ำอัตโนมัติ |
| ป้าย false positive/negative ผิด | ต้องมีการยืนยันจากคน และผู้ตรวจคนที่สองสำหรับ sec |
| เทรนซ้ำแล้วโมเดลแย่ลงในด้านอื่น | regression eval เต็มทุกรอบ และ rollback ตามระยะ 5 |
| ภาระคนตรวจล้นคิว | จัดลำดับความสำคัญ จำกัดจำนวนที่นำเข้าคิวต่อวัน |
